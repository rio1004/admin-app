# Item milestone

Items are available at `/admin/items` with create, edit, detail, and delete screens matching the existing admin design. Lists support name/slug search, category filtering, allowlisted sorting, and server pagination at 10 records per page. Pagination preserves the query.

## Setup

```sh
php artisan migrate
php artisan storage:link
npm run build
```

Existing Admin accounts already hold item permissions. No example items or categories are seeded. Create a category before adding an item. The dashboard displays real permission-aware totals and the five newest items.

## Fields and access

- Required name, up to 120 characters.
- Required category with a restrictive database foreign key.
- Nullable image stored as a generated path on the `public` disk; pages receive a separate URL, not a writable storage path.
- Nullable HTTP/HTTPS link, up to 2048 characters.
- Automatically generated, read-only slug backed by a unique index. Duplicate names get numbered suffixes, empty generated slugs fall back to `item`, and renaming preserves the slug. Concurrent unique-key collisions retry.

All routes require authentication and `admin.access`. List/detail use `items.view`; create, edit/update, and delete use their corresponding action permissions. Navigation and actions use the same capabilities. Item forms may access category IDs/names without category-management permission; they do not grant category editing access.

## Images

Uploads accept JPEG, PNG, and WebP content, up to 5 MB and 4096 by 4096 pixels. SVG and other formats are rejected. Filenames are generated by the server.

- No new image and no removal flag: preserve the image.
- New image: replace the image; delete the obsolete file after commit.
- Explicit `remove_image`: clear the reference and delete the file after commit.
- Both upload and removal: reject the request.

Failed writes clean up new uploads while preserving old files and database values. An outer transaction rollback cleans up the new upload too. Item deletion removes the image only after the database deletion commits. Failed storage writes return an inline image validation error. Cleanup failures are logged as `Item image cleanup failed.` without reporting a committed database save as failed; operators can retry removing that orphaned path from storage. Only generated paths within `items/` can be deleted. Client-provided image paths are rejected.

The existing public disk serves images via `/storage`; `storage:link` must exist for browser previews. No cloud storage configuration or credentials are changed.

## Category protection

`Category::items()` and `Item::category()` are active Eloquent relationships. Category deletion locks the parent row and checks real item usage. `items.category_id` uses `restrictOnDelete()`, so direct deletion is also rejected. Foreign-key deletion failures become actionable category validation errors. Item writes lock the selected parent category before saving and report a category removed after validation. Empty categories can be deleted after their items are reassigned or deleted.

## Verification

```sh
php -d extension=pdo_sqlite vendor/bin/pest
powershell -NoProfile -File scripts/test-mysql.ps1
composer lint:check
composer types:check
npm run check
npm run types:check
npm run build
```

The MySQL script creates and removes a disposable test database. Two-process integration tests verify both outcomes of concurrent category deletion and item insertion. Upload tests use fake storage and cover keep/replace/remove, validation, database failures, rollback, storage failures, and post-commit cleanup failures.

No user CRUD or deployment is included.
